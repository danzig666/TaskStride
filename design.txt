Build a complete, production-quality, open-source web application that acts as a beautiful modern frontend for **Google Tasks**.

Working name: **TaskStride**. Keep the name, logo and accent color easy to change from one configuration file.

The application must use the user's real Google Tasks data through the official Google Tasks API. Google Tasks must remain the source of truth. Do not create a separate cloud database, custom account system, or proprietary task store.

The result should feel like a premium native productivity application, not an admin dashboard and not a clone of Google's current Tasks UI.

The application must work exceptionally well on:

* desktop browsers
* laptops
* tablets
* Android phones
* iPhones
* installed as a PWA

It must provide equally polished **light and dark themes**.

## 1. Core product philosophy

The app should have the simplicity of Things / Todoist / Linear-style interfaces while remaining faithful to the Google Tasks data model.

Prioritize:

1. extremely fast interaction
2. minimal visual clutter
3. excellent typography
4. useful information density
5. keyboard efficiency on desktop
6. touch efficiency on mobile
7. immediate visual feedback
8. excellent dark mode
9. graceful Google API error handling
10. no fake functionality that Google Tasks cannot actually synchronize

Every task-changing action must ultimately modify the real Google Tasks resource.

Do not create fake synchronized features such as:

* priority fields
* arbitrary tags
* task colors
* due times
* reminders
* recurrence rules

unless the Google Tasks API genuinely exposes a reliable writable equivalent.

Local-only UI preferences are allowed, but clearly keep them separate from task data.

Examples of acceptable local-only state:

* theme
* compact/comfortable density
* sidebar collapsed state
* favorite task lists
* list accent colors
* last selected view
* onboarding completed state

## 2. Technical stack

Use a modern TypeScript stack.

Preferred:

* React
* TypeScript with strict mode
* Vite
* Tailwind CSS
* shadcn/ui or high-quality Radix-based primitives where useful
* Lucide icons
* TanStack Query for server state
* Zustand only for small amounts of client UI state
* dnd-kit for accessible drag-and-drop
* date-fns for date calculations
* IndexedDB through Dexie or an equally lightweight abstraction for local cached data
* Vite PWA plugin / Workbox for PWA support
* Vitest
* React Testing Library
* Playwright for critical end-to-end tests

Use current stable package versions rather than blindly pinning outdated versions.

Avoid unnecessarily large dependencies.

Do not use Next.js unless there is a concrete technical reason. The target is primarily a static SPA that can be hosted by nginx/Apache with no Node server running in production.

## 3. Architecture

The default deployment architecture should be:

browser
→ Google Identity Services
→ Google Tasks REST API

There should be **no application backend required for normal operation**.

The generated build should consist of static assets that can be hosted from any HTTPS web server.

Support both:

* deployment at domain root
* deployment below a configurable subpath such as `/tasks/`

Do not hardcode the root path.

Use environment configuration such as:

* Google OAuth client ID
* app base path
* optional application display name

Never include a Google client secret in frontend code.

Never store OAuth access tokens in localStorage or IndexedDB.

Keep OAuth tokens in memory.

## 4. Google authentication

Use **Google Identity Services**.

For the zero-backend configuration, use Google's supported browser token model.

Request only the Google Tasks read/write scope needed by the application.

Implement:

* Connect Google Account
* account authorization
* authorization error handling
* expired-token detection
* reconnect flow
* revoke/disconnect flow
* clear cached user task data when disconnecting

Because browser access tokens are short-lived and cannot be silently refreshed with a server-side refresh token in this architecture, handle expiration elegantly.

Do NOT create a fake silent-refresh implementation.

When authorization expires:

* keep the cached task UI visible
* place the interface into a clearly identifiable disconnected/read-only state
* display a small non-obtrusive "Reconnect Google" control
* retry the requested action after reconnection when safe
* never discard an unsaved user edit without warning

The authorization state should not dominate the UI.

### Critical due-date rule

Google Tasks exposes a **date**, not a writable time-of-day.

Therefore:

* the UI must use date-only due dates
* never show a fake due time
* never offer "remind me at 16:00"
* do not store an arbitrary time in the API value and pretend it will survive synchronization

Use the user's local timezone only for interpreting/displaying the calendar date safely.

Avoid common UTC conversion bugs where a task due today appears due yesterday or tomorrow.

Write unit tests specifically for date handling around UTC offsets and DST boundaries.

## 7. Repeating and assigned tasks

Google can return task types that have restrictions not shared by ordinary tasks.

Detect these gracefully.

For assigned tasks originating in Google Docs or Google Chat:

* show a subtle origin badge
* display the assignment/source context if available
* provide an "Open source" action when a source link exists
* respect read-only fields
* do not allow unsupported nesting operations
* warn appropriately before destructive actions that can affect the original assignment

If the task exposes Gmail/source links, show a small source icon and allow opening the source.

For repeating/recurrent tasks returned by Google:

* display them correctly
* do not invent a recurrence editor if recurrence rules are not exposed as writable data
* do not allow cross-list movement when Google disallows it
* do not allow nesting actions Google disallows

Prefer disabling unavailable controls with a concise tooltip rather than letting the API request fail.

## 8. Synchronization model

The UI should feel instant.

Use:

* TanStack Query cache
* optimistic mutations
* rollback on failure
* background refresh
* incremental synchronization where appropriate

At application start:

1. restore the cached view immediately from IndexedDB if available
2. authenticate/reconnect if needed
3. fetch task lists
4. fetch current task data
5. reconcile cache with Google

After successful mutations:

* update local UI immediately
* send the API request
* reconcile with the returned authoritative Google object

When returning to the tab:

* refresh stale data

Also refresh when:

* browser regains network
* user explicitly pulls/requests refresh
* app returns from background after a reasonable interval

Do not hammer the Google API continuously.

Provide a subtle sync-state indicator:

* synced
* syncing
* offline
* reconnect required
* sync error

Do not put a giant persistent "SYNCED" banner on screen.

## 9. Offline behavior

Make the PWA shell usable offline.

Cache:

* application assets
* recent task lists
* recent tasks
* local UI preferences

Offline requirements for the first production version:

* existing cached tasks can be browsed
* search works over cached data
* task detail views work
* theme/settings work

For task mutations while fully offline, choose one of two safe approaches:

A. implement a robust IndexedDB mutation queue with clear pending state and conflict recovery

or

B. initially make modifications unavailable offline and explain succinctly that reconnecting is required

Do not implement a fragile half-working offline queue.

If you implement queued offline writes, each queued item must have:

* unique local mutation ID
* creation timestamp
* mutation type
* task/list target
* payload
* processing status
* retry count
* failure reason

Queued writes must be visible as pending.

## 36. API conflict strategy

Google remains authoritative.

If data changes remotely:

* merge newly fetched authoritative task objects into cache
* preserve pending local edits carefully
* don't duplicate tasks
* don't silently resurrect deleted tasks

Use Google task IDs as canonical identity.

Use ETags/updated timestamps for detecting changed objects where useful.

If a conflict cannot safely be merged:

* retain the remote authoritative object
* preserve the user's unsaved text locally temporarily
* explain the conflict
* allow the user to copy/reapply their edit

Never silently discard typed notes.

## 37. API efficiency

Use task list pagination.

Use task pagination.

Where beneficial, request only required response fields.

Use `updatedMin` for incremental refresh where it produces correct synchronization.

When doing incremental synchronization, ensure deleted/hidden items are handled correctly so stale tasks do not remain visible forever.

Periodically perform a full reconciliation rather than relying indefinitely on incremental state.
